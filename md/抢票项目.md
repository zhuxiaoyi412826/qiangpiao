# 演唱会秒杀抢票项目整体功能梳理

整体分为：**用户前端（抢票 H5 / 网页）、后端 API 服务、后台管理系统（运营后台）**，同时还要考虑秒杀核心的高并发、防刷、库存、订单、支付逻辑。

## 一、用户端前端页面（普通用户访问，抢票客户端）

> 可以是 PC 网页、H5 移动端页面、小程序，这里以 Web 网页为例

### 1. 首页 / 演唱会列表页

- 演唱会活动列表展示：海报、演出名称、演出时间、地点、状态（未开售｜即将开售｜秒杀中｜已售罄｜已结束）
- 筛选：按城市、时间筛选演出
- 活动倒计时（距离开售倒计时）
- 点击进入详情

### 2. 演唱会详情页（核心页面）

- 顶部海报、演出基础信息：艺人、时间、场馆地址
- **票价档位选择**：不同价位票档、剩余库存展示（注意：秒杀场景不要真实实时返回精确库存，做库存脱敏）
- 选座模块（两种模式：①无选座，直接抢票随机分配；②在线选座，座位图 SVG 可视化选座）
- **开售倒计时组件**，未到时间按钮置灰不可点击
- 实名观演人选择：添加 / 维护观演人信息（实名身份证、姓名，一票一证）
- 抢票按钮：倒计时结束后激活秒杀提交按钮
- 活动规则弹窗：限购说明、退票规则

### 3. 秒杀抢票提交页面（核心交互）

- 防重复提交：点击之后按钮置灰，loading 状态
- 请求排队提示：“正在排队，请不要刷新页面”
- 返回结果： ✅抢到 → 跳转确认下单页面 ❌没抢到 → 提示售罄 / 排队失败，请重试

> 重点：前端只能做交互拦截，**真正的库存判断、限购校验全部放在后端**，前端不能信任

### 4. 订单页面

- 待支付订单列表（限时支付，比如 15 分钟未支付自动释放回库存）
- 已支付订单、已完成、已取消订单
- 订单详情：演出、座位、观演人、二维码电子票
- 电子票展示（核销二维码）
- 退票申请入口（后台配置是否允许退票）

### 5. 用户个人中心

- 登录注册（手机号验证码登录）
- 观演人管理（实名信息维护）
- 我的订单、我的票务
- 收货（实体纸质票邮寄，如果需要）

### 6. 辅助页面

- 支付跳转页（对接微信 / 支付宝）
- 退票进度查询
- 公告页

**前端秒杀层面需要做的防御：**

1. 倒计时以**服务器时间为准，不能只用本地 JS 时间**（防止本地改系统时间提前抢票）
2. 按钮防抖、短时间禁止重复点击
3. 简单人机验证：滑块验证码 / 图形验证码（正式防刷还需要后端限流）

## 二、后端管理页面（运营后台，管理员使用）

### 📌演出活动管理模块

1. 演唱会活动 CRUD
   - 新增演出：上传海报、填写艺人、场馆、演出日期、演出简介
   - 设置**开售时间、结束抢票时间**
   - 设置限购规则：每个账号最多买几张票
   - 设置退票策略：是否允许退票、退票截止时间、退票手续费
2. 票档与库存设置
   - 新增票价档位：价位名称、价格、总库存
   - 如果开启选座模式：导入座位数据（场馆座位模板）
   - 库存初始化；**注意秒杀业务，库存不要直接操作数据库，需要预热到 Redis**
3. 活动上下架；暂停活动

### 📌订单管理模块

1. 全部订单查询：按演出、时间、订单状态筛选（待支付、已支付、已核销、已取消、已退票、超时自动关闭）
2. 订单详情查看：观演实名信息、票档、座位号
3. 手动退款（后台运营退款）
4. 超时订单统计；导出订单报表（Excel）

### 📌票务核销管理（现场检票）

1. 电子票核销后台：输入票号或者扫码核销二维码
2. 核销记录；防止一票多次核销
3. 核销数据统计，已入场人数

### 📌用户 & 观演实名管理

1. 用户账号列表；禁用用户（针对黄牛账号）
2. 查看用户名下实名观演人信息；不允许后台随意修改实名（实名只读）

### 📌风控 & 秒杀监控模块（后台非常关键）

1. 秒杀实时监控面板：
   - 当前访问 QPS 监控、剩余库存实时看板
   - 排队请求量监控
2. 黑名单管理：拉黑 IP / 拉黑账号，限制抢票（防黄牛脚本）
3. 限流策略配置：单账号一段时间请求频次限制
4. 验证码策略开关（是否开启抢票验证码）

### 📌系统基础模块

1. 管理员账号、角色权限；不同运营角色（普通运营、超级管理员）
2. 系统日志：操作日志、秒杀异常日志查看
3. 公告管理（发布前端首页活动公告）

## 三、后端服务核心业务功能（接口层，不属于页面，但是项目必须实现）

> 秒杀重点难点部分

1. 用户登录认证；观演人实名接口
2. 秒杀核心逻辑（高并发）
   - Redis 预减库存；消息队列异步创建订单（削峰）
   - 超时未支付，定时任务回滚释放库存
   - 一人限购校验；防止超卖（超卖是秒杀最大坑）
3. 订单服务：生成订单、超时关闭订单
4. 支付回调处理（支付成功更新订单状态）
5. 退票逻辑：退票之后库存回补（注意回补不要直接放回秒杀池，防止二次瞬间抢空）
6. 风控限流：接口层 IP 限流、账号访问频次限制；验证码校验
7. 电子票生成；核销接口
8. 库存预热脚本：活动开始前把库存数据加载进 Redis

## 四、两种业务方案选型（是否开启选座）

表格

| 模式           | 说明                                                         | 适用场景               |
| -------------- | ------------------------------------------------------------ | ---------------------- |
| 无选座随机出票 | 抢到票之后系统自动分配座位；前端无需座位图；实现简单，并发更高 | 热门演唱会纯秒杀       |
| 在线选座秒杀   | 先选座位再提交；前端 SVG 座位图；后端维护座位锁；并发压力更大，容易出现座位锁冲突 | 希望用户自选位置的演出 |
