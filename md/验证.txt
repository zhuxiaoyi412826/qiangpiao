零 SQL 验证清单（全走页面/接口）
1. 建表是否生效
后台 → 车次管理 → 任意车次行 → 「区间库存」

预期：提示「已初始化 N 个区间库存段」（N = 经停站数 − 1）。若表缺失会直接报错或返回 0，说明脚本没跑全。

2. 造一个 3 站车次（只在需要验证"分段复用"时做）
后台 → 该车次行 → 「时刻表」 → 「添加停靠站」，数组顺序即站序，填三行：

顺序	车站	到站	发车	停站(分)
1	始发站	—	08:00	0
2	沿线某中间站	09:00	09:02	2
3	终到站	10:30	—	0
保存后**再点一次「区间库存」**重新初始化（段数会从 1 变 2）。

3. 区间余票
前台车次详情带参访问：http://localhost:5173/trains/1?from=北京南&to=德州东，或列表页直接搜中途站→终点站点进详情。

预期：

不同类型区间（如 1→2、2→3、1→3）显示的余票可以不同（取覆盖各段的最小值）；
座位图里只有「本区间被占」的座位是灰的，其它区间被占的座位仍可选。
这一条过了，说明区间库存 + 区间座位图都生效。

4. 同座位分段复用（最关键）
用两个账号分别下单：

?from=北京南&to=德州东 买一张
?from=德州东&to=上海虹桥 买一张
然后看订单列表 / 订单详情的「车厢 + 座位号」。

预期：两张票车厢座位号相同；订单上的上/下车站点是区间站，不是始发终到。这就是复用成功的直接证据，不用查库。

5. 售卖时间窗口
后台 → 车次行 → 「售卖窗口」：

开始时间填未来（如 2030-01-01 00:00:00）→ 前台抢票应返回 code=4018（未开始售卖）
开始留空、结束填过去（如 2020-01-01 00:00:00）→ 返回 code=4019（已停止售卖）
两栏都留空保存 → 抢票恢复正常
6. SSE 推送
F12 → Network → 抢票，应看到 stream 请求类型为 eventsource，EventStream 页签里先 connected、随后毫秒级收到 seckill-result 带车厢座位号。命令行等价验证：

bat
curl -N -H "Accept: text/event-stream" "http://localhost:8080/qiangpiao/api/seckill/stream?batchNo=<BATCH_NO>&token=<TOKEN>"
（另一个窗口先发起抢票拿到 batchNo 再订阅，或订阅后立刻抢）

7. 兼容性回归
换一个**没点过「区间库存」**的车次走完整流程（查询 → 下单 → 支付 → 退票）。

预期：与改造前完全一致。这条证明"表没数据时自动退化为全程票"的兜底是好的。

8. 链路追踪 traceId（响应体 / 响应头 / 日志 三者一致）
重新打包部署后，任意接口都应带回 traceId：

```bat
curl -i http://localhost:8080/qiangpiao/api/trains/1
```

预期：响应头 X-Trace-Id 与响应体里的 "traceId" 完全一致（不再是 null）。
失败响应同样带（全局异常处理器走同一个 R.build()）。

再用这个 ID 捞日志，应串起整条链路：

```bat
findstr /i "上一步的traceId" D:\rizi1\qiangpiao\info-2026-09-30.log
```

预期：能看到 [http-nio-8080-exec-N] 的「请求开始 → 业务日志 → 请求结束」；
抢票时还能看到 [seckill-N] 线程的下单日志带同一个 traceId —— 证明异步线程 MDC 传递生效
（改造前异步落库日志的 traceId 是空的，请求线程和落库线程对不上账）。

慢请求单独进 warn 日志（>1s 自动打 warn）：

```bat
findstr /i "cost=" D:\rizi1\qiangpiao\warn-2026-09-30.log
```

前端：随便触发一个失败（如抢已售完的车次），toast 文案末尾应带「（traceId：xxxxxxxx）」，
复制它到日志里一搜即可定位。

9. JWT 登出 / 强制下线（token 黑名单）
注意：改造前签发的老 token 没有 jti，拉黑不了 —— 先重新登录一次再验。

```bat
:: 1) 登录（新 token 带 jti）
curl -X POST http://localhost:8080/qiangpiao/api/auth/login -H "Content-Type: application/json" -d "{\"username\":\"你的账号\",\"password\":\"你的密码\"}"

:: 2) 用 token 访问受保护接口 → 200
curl -H "Authorization: Bearer <TOKEN>" http://localhost:8080/qiangpiao/api/auth/info

:: 3) 登出
curl -X POST http://localhost:8080/qiangpiao/api/auth/logout -H "Authorization: Bearer <TOKEN>"

:: 4) 再用同一个 token 访问 → 必须 401（这正是原来做不到的）
curl -i -H "Authorization: Bearer <TOKEN>" http://localhost:8080/qiangpiao/api/auth/info
```

第 4 步返回 401 即核心能力生效。前端表现：点「退出」后，旧 token 调任何接口都会被弹回登录页。

强制下线（管理员）：

```bat
curl -X POST "http://localhost:8080/qiangpiao/api/admin/users/3/kick" -H "Authorization: Bearer <ADMIN_TOKEN>"
```

返回 0 = 对方没有在线登录态，>0 = 被拉黑的 token 数，随后该用户所有端都 401。
也可以在后台「用户管理」每行直接点「强制下线」按钮。

封号即时生效：后台把用户状态改成「已封禁」，该用户已签发的 token 会被同步拉黑，
不用等 token 自然过期。

Redis 侧核对（可选，验证 TTL 跟着剩余寿命走，不是永久 key）：

```bat
redis-cli keys qp:token:blacklist:*
redis-cli ttl qp:token:blacklist:<jti>
redis-cli smembers qp:token:user:<userId>
```

预期：ttl ≈ token 剩余秒数（≤ jwt.expiration 配置值）；登出后该用户 Set 里对应 jti 已移除。
把 Redis 停掉再访问接口应仍正常（黑名单降级放行，可用性优先）。
